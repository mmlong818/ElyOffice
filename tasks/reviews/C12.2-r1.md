- crates/ely-mail-engine/src/mime.rs:198 — [P1] Text attachments lose their original file bytes. `MessagePart::contents()` returns charset-decoded UTF-8 for `text/*`, rather than just transfer-decoded octets. A `text/plain; charset=iso-8859-1` attachment containing quoted-printable `Caf=E9` becomes `[67,97,102,195,169]` instead of `[67,97,102,233]`. Building and reading a `text/plain` attachment with those original bytes instead produces `[67,97,102,239,191,189]`. Saving or forwarding therefore changes the file silently. Preserve attachment octets after transfer decoding; apply charset conversion separately to displayed bodies. Add non-UTF-8 text attachment tests; the existing every-byte test only covers `application/octet-stream`. Both failures are recorded in `.work/C12.2-r1/probes.log`.

- crates/ely-mail-engine/src/mime.rs:104 — [P2] HTML body selection ignores `multipart/related`'s `start` parameter. With `type="text/html"; start="<root@example.com>"`, an image first and the HTML part with that Content-ID second, `read` returns `html: None` and puts both parts in `inline`. The actual message body is thus unavailable despite its explicit root declaration. Resolve the related root from `start` before choosing body parts, using the first child only when `start` is absent, as specified by [RFC 2387 §3.2](https://www.rfc-editor.org/rfc/rfc2387.html#section-3.2). Add this ordering to the MIME tests. Reproduced by `a_related_html_root_can_come_after_its_image` in the probe log.

- crates/ely-mail-engine/src/mime.rs:81 — [P2] An attached multipart entity disappears as an attachment and its contents become the parent message's body. For an outer `multipart/mixed` containing plain `body` followed by `multipart/alternative` with `Content-Disposition: attachment; filename=alternatives.mime`, whose text child contains `private attachment`, `read` returns `text: Some("body\nprivate attachment")` and zero attachments. The parent's disposition applies to the whole multipart entity ([RFC 2183 §2.9](https://www.rfc-editor.org/rfc/rfc2183.html#section-2.9)). Respect that disposition while traversing the MIME tree, retain the attached entity, and exclude its descendants from the main bodies. Add a regression for this structure; `multipart_attachment_is_not_displayed_as_parent_body` reproduces both incorrect outputs.

- crates/ely-mail-engine/src/mime.rs:228 — [P2] Joining every body part concatenates mutually exclusive alternatives. A `multipart/alternative` with an ASCII plain-text version `Cafe` followed by its UTF-8 plain-text version `Café` yields `Some("Cafe\nCafé")`. The reader cannot subsequently select a representation because the alternatives and their container relationship have already been discarded. Select the supported alternative within each alternative container instead of joining its siblings; concatenation can remain for independent mixed body segments. [RFC 2046 §5.1.4](https://www.rfc-editor.org/rfc/rfc2046.html#section-5.1.4) specifies alternative selection. Add a same-type alternative regression; `alternatives_of_the_same_type_are_not_concatenated` fails in the probe log.

- crates/ely-mail-engine/src/mime.rs:186 — [P2] The missing Content-Type default is wrong for children of `multipart/digest`.
